## Where to spend the additional time

- **3 · Projects:** connect each example to one engineering responsibility: joining meetings, capturing audio, coordinating avatars, and handing a SIP call to a human. Explain that testing depends on the application's job.
- **5 · System:** point separately to the input path, tool request/result, and output path. Ask where an interruption or timeout can change the outcome. Clarify that SIP signaling and media transport are different responsibilities.
- **6–7 · Continuous voice:** identify the media path, delegated reasoning/tools, and application control. Trace one changed request through the existing sequence. Explain result correlation: an answer to the old task cannot satisfy the new instruction. These diagrams are an architecture pattern, not a claim about the projects on slide 3.
- **8 · Four dimensions:** name one measurement per dimension: received audio/turn timing, correction retention, tool arguments versus confirmed values, and required goal steps. Open **Conduct** for about 40 seconds: the agent confirms 40 but retains 14 in a stale draft. A schema can validate the shape while the value violates the agreed request. Close it before advancing.
- **9 · Timing:** compare both endpointing states and ask the audience what the shorter interval misses. Explain system end-of-turn → received audio versus the caller's actual finished request. Restore patient endpointing.
- **10–11 · Requirements and workbench:** distinguish an observable conversational goal from independently verified backend state. Explain that running a changed agent creates new interaction evidence; re-scoring a saved conversation only changes its evaluation.
- **14 · vCon:** spend 25 seconds on requirement/finding, 25 following dialog[1] to the agent statement, and 25 on the unknown cancellation outcome. “One supported behavior does not establish business completion.” The richer review is an illustrative application payload, not a literal CAE export; do not read the JSON aloud.
- **15 · ASSERT:** walk several requirements, a reviewed case, voice execution, and individual judgments. Open **Engineering details** for about 30 seconds to show setup → saved call → judgment; skip the artifact and statistics disclosures. “A requirement is one behavior within the broader scenario. ASSERT supplies a reusable Python workflow, not just Markdown or a more accurate model.”
- **16 · Judge reliability:** open **Check facts** for about 30 seconds. The caller corrects 14 to 40, but the agent's spoken readback is 14. This is a different failure from slide 8's correct spoken readback and stale tool draft. Then explain held-out human labels: count missed failures and false alarms, review disagreements, and keep hard failures out of an average. Leave the provider comparison closed.
- **17 · Release:** pause for the audience's release decision. Walk speed, each regression, and the hold. Counts can overlap; zero observed errors in a sample does not mean zero production risk. Keep the statistical derivation for Q&A.
